# Правила работы Codex в репозитории

Применяй эти правила ко всем последующим задачам в этом репозитории. Перед изменениями изучай существующий код и документацию; меняй чужие модули только при необходимости. Не создавай лишние файлы и функциональность. Не выполняй commit или push без разрешения. Не выводи полный код файлов без запроса. В Python используй одинарные кавычки.

## Стек и границы

- Backend: Python 3.12, FastAPI, PostgreSQL, SQLAlchemy, Alembic, pytest, Docker. Frontend по спецификации MVP — React.
- Разделяй API, сервисы предметной области, слой БД и адаптер скоринга. Backend отвечает за PostgreSQL, авторизацию, заявки, локальные моки ФНС/БКИ, бизнес-правила, кредитные решения, альтернативные условия и аудит.
- ML-участник отдельно отвечает за генерацию синтетических обучающих данных, обучение, валидацию и версионирование модели. Mock scoring ещё не реализован; при реализации сделай его детерминированным и явно помечай тестовые результаты. Сохраняй единый версионированный контракт входа/выхода из `docs/00_common.md`, чтобы заменить mock моделью без изменения бизнес-логики.
- Разделяй оценку риска дефолта, бизнес-правила и кредитное решение. Низкорисковые заявки могут получать автоматическое решение по версионированным правилам, пограничные передаются сотруднику. Условия продуктов, лимиты и пороги из `docs/00_common.md` обозначай только как демонстрационные допущения; не приписывай их Альфа-Банку.
- Единая FSM и будущий публичный API-контракт определены в `docs/00_common.md`. Backend сохраняет каждый фактический переход в `status_events`; frontend показывает текущий статус и историю без фиктивной анимации. Текущие маршруты FastAPI `/health` и `/docs` сохраняются; nginx позднее публикует API с префиксом `/api`.
- Новостная лента исключена. Подписание и выдача допускаются только как локальная демонстрационная имитация без внешних SMS. Docker-запуск обязателен, публичное размещение желательно.
- Используй только синтетические данные и локальные моки интеграций. Реальные банковские интеграции и данные запрещены в MVP.

## Безопасность и надёжность

- Следуй применимым практикам [OWASP ASVS](https://asvs.owasp.org/), [OWASP API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10/) и [NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final). Учитывай угрозы из `docs/threat-model.md`. Не заявляй о полном соответствии банковским стандартам без независимой проверки.
- Проверяй и ограничивай входные данные; обеспечивай аутентификацию, RBAC и принадлежность/назначение каждого объекта на сервере. Не храни секреты в коде, Git, логах или образах.
- Используй транзакции, ограничения целостности, явную обработку ошибок и идемпотентность критичных операций. Не превращай технический сбой скоринга или мока в кредитный отказ либо одобрение.
- Проверяй допустимые переходы состояний. Аудируй решения и действия сотрудника; сохраняй версии снимков данных, правил, схемы признаков и адаптера/модели.
- Фиксируй зависимости и версии базовых образов; применяй безопасные настройки Docker с минимальными правами и без секретов в образе.

## Проверки и отчёт

- На каждом этапе запускай применимые тесты, линтеры и доступные проверки безопасности. Добавляй содержательные тесты на ошибки, запрещённые переходы и нарушения прав доступа. Если инструмента или тестов ещё нет, явно укажи это в отчёте; не создавай CI без задачи на него.
- После задачи кратко сообщай: изменённые файлы, результаты проверок, непроверенные требования и оставшиеся риски.
