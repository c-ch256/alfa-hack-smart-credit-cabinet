# Craftors — ML ↔ Backend: входные данные и результаты (v1)

**Основа:** `docs/00_common.md`, разделы 7, 9, 10, 13. Это контракт **инференса**, не обучающий датасет. Изменения согласовывать с backend и фиксировать в общем документе.

## Файлы
- `scoring_request.schema.json` — поля, типы, обязательность `ScoringRequest`.
- `scoring_result.schema.json` — формат `ScoringResult`.
- `scoring_requests.json` — три синтетических кейса для тестирования интерфейса; из каждого элемента в `Scorer.score()` передаётся **только** значение ключа `request`.

## Выход ML
`ScoringResult = {pd, risk_band, model_version, reasons}`.
- `pd`: вероятность дефолта, число от 0 до 1. Например, `0.031` = 3,1%.
- `risk_band`: A при PD < 0.05; B при 0.05 ≤ PD < 0.10; C при 0.10 ≤ PD < 0.20; D при PD ≥ 0.20. Обязательно согласуется с PD.
- `model_version`: идентификатор реально используемого скорера/артефакта.
- `reasons`: массив объяснений; `feature`, `text`, `effect` (`increases_risk`/`decreases_risk`), `contribution` (число). Если числовой вклад нечестно вычислить, не подставлять фиктивное значение — лучше вернуть пустой массив и согласовать упрощение с backend.

## Граница ответственности
`ModelScorer` и `MockScorer` реализуют **один** интерфейс `Scorer.score(req: ScoringRequest) -> ScoringResult`. Backend создаёт запрос, вызывает скорер, сохраняет результат, а **кредитная политика** решает approve/counter_offer/manual_review/reject. ML не меняет статус заявки и не выдаёт кредит.

Не все заявки передаются в ML:
- `client4`: компания в ликвидации, просрочка 120 дней → стоп-фактор на `checking`, отклонение **до скоринга**.
- Инвестиционный кредит 8 млн ₽ без требуемого залога → `needs_info` на `checking`, запрос дополнительных сведений **до скоринга**.
- `client3`: просрочка 45 дней → решение `manual_review` по правилам кредитной политики; значения PD не отменяют это правило. Выполнит ли backend скоринг перед ручным рассмотрением — определяется согласованным workflow.

## Производные признаки
Из базовых входных данных можно вычислить отношение кредита к годовой выручке, покрытие залогом и другие признаки **одним и тем же кодом** при обучении и при инференсе. Аннуитетный платёж и DSCR зависят от ставки. Поскольку ставка по ТЗ зависит от возвращённой категории риска, нельзя молча считать итоговый DSCR в ML по ставке, неизвестной до получения PD: предварительную ставку/правило расчёта надо согласовать отдельно. Финальное решение по DSCR принимает backend после определения условий кредита.

## Важные оговорки
- **Эти 3 записи — синтетические тесты интеграции, не данные для обучения и не проверка качества модели**; в них нет истинных меток фактического дефолта.
- В `client2` и `client3` не перечисленные в исходном ТЗ показатели дополнены демонстрационными допущениями. Они не банковские данные.
- Не придумывать обучающие метки из желаемых решений (`approve` и т.п.): статус одобрения **не равен** факту дефолта.
- Кредитный кабинет показывает пользователю только понятные причины, а не PD или веса модели; сотрудник может видеть расширенные данные.
- Внешние ФНС/БКИ интеграции не нужны: используем исключительно моки и синтетические данные.
