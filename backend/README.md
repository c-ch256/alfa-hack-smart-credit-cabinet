# Backend: FastAPI и PostgreSQL

Python 3.12, FastAPI, PostgreSQL 16, SQLAlchemy 2.0 и Alembic. Реализованы `/health`, `/ready`, авторизация, клиентский API черновиков и переходы `submit`/`withdraw`. `/health` проверяет процесс API; `/ready` делает `SELECT 1` в БД и возвращает 503 при недоступности без деталей подключения.

## Запуск через Docker Compose

Режим скоринга задаёт `SCORER=mock|model` в `.env` (по умолчанию `mock`).
После смены режима пересоздайте API: `docker compose up -d --build --force-recreate api`.
В режиме `model` образ содержит доверенный локальный артефакт `ml/artifacts/pipeline.joblib`
и минимальные runtime-зависимости инференса; сеть при запуске модели не нужна.
`MODEL_DIR` в контейнере по умолчанию `/app/ml/artifacts`. Для локального запуска
backend можно задать `MODEL_DIR` абсолютным путём к каталогу артефакта; без него
используется `ml/artifacts` в корне репозитория. При несовместимости зависимостей,
исходников preprocessing или хеша pipeline приложение в режиме `model` не стартует
с контролируемой технической ошибкой; тихого перехода на mock нет.

Для проверки модели локально: из корня репозитория запустите
`PYTHONPATH=backend:. python -m pytest -q backend/tests/test_model_scoring.py backend/tests/test_model_workflow.py`
в окружении backend с установленными зависимостями `backend/requirements-dev.lock`.
Модель обучена на синтетических данных. Её PD и метрики не подтверждают качество
на реальных заёмщиках; результаты сохраняются с `source=model` и
`is_test_result=True`, а кредитное решение остаётся за backend policy.

Из корня репозитория:

```bash
cp .env.example .env
# Задайте в .env собственные DB_PASSWORD, JWT_SECRET и DEMO_PASSWORD.
docker compose up --build
```

После первого запуска: `http://127.0.0.1:8000/health`, `http://127.0.0.1:8000/ready`, Swagger `http://127.0.0.1:8000/docs`. Compose не публикует порт PostgreSQL, API доступен только на localhost. Данные БД сохраняются в именованном volume `postgres_data`; обычный `docker compose down` его не удаляет. API работает без root и запускает миграции, идемпотентный seed учётных записей и Uvicorn. При ошибке миграции или seed контейнер API не стартует.

`JWT_SECRET` должен содержать не менее 32 байт случайного значения, `DEMO_PASSWORD` — не менее 12 символов. Эти значения не коммитят и не передают в логи. Seed создаёт `client1`–`client4` (CLIENT), `staff1` (STAFF), четыре синтетические компании и два демонстрационных продукта. Повторный запуск не меняет существующие учётные записи, пароли и компании; смену пароля нужно выполнять отдельной процедурой. Заявки seed не создаёт.

Если `DEMO_PASSWORD` в `.env` изменён после первого seed, пересоздайте API-контейнер для загрузки нового окружения и выполните отдельную команду:

```bash
docker compose up -d --force-recreate api
docker compose exec api python -m app.reset_demo_passwords
```

Команда меняет только хеши паролей существующих `client1`–`client4` и `staff1`; отсутствующие учётки не создаёт. Для локального Conda-запуска из `backend/` используйте `conda run -n craftors-backend python -m app.reset_demo_passwords` после передачи `DEMO_PASSWORD` через окружение. Пароль и хеш команда не печатает.

`KEY_RATE` задаёт демонстрационную базовую ставку в процентах годовых (по умолчанию `14.00`); это ручное допущение MVP, а не ставка из внешнего источника или тариф банка. `app.services.pricing` рассчитывает ставку, аннуитет, итог выплат и DSCR в целых рублях с арифметикой `Decimal`. `app.services.mocks` содержит фиксированные синтетические ответы ФНС/БКИ для четырёх демо-ИНН. `app.services.checks.run_checks(session, application, snapshot)` добавляет три результата к указанному снимку, сохраняя прежние результаты. Результаты БКИ и служебные коды не выдаются клиентским API.

`app.scoring.base` задаёт версионированный контракт `Scorer.score(ScoringRequest) -> ScoringResult`; `app.scoring.mock.MockScorer` — детерминированная синтетическая скоркарта с версией `mock-demo-2026-1`, не обученная модель. `app.services.policy.evaluate_policy` применяет учебные пороги и перебирает допустимые условия. `app.services.workflow.submit_and_process` связывает проверки, скоринг, политику и существующую FSM. В одной транзакции сохраняются новый снимок заявки и компании, проверки, попытки скоринга, решение/предложение при наличии, события статуса и аудит. Ошибки мока/скоринга оставляют заявку в `checking`/`scoring` и записывают попытку без кредитного отказа. Повторный `submit` в таком состоянии выполняет ограниченную повторную попытку; после успешного завершения возвращает 409. В production синхронную обработку следует вынести в очередь, сохранив транзакционные переходы и защиту от повторов.

Проверка состояния и текущей миграции:

```bash
docker compose ps
docker compose exec api alembic -c alembic.ini current
```

## Локальная разработка в Conda

Все установки и проверки выполняйте только в окружении `craftors-backend`:

```bash
conda run -n craftors-backend python -m pip install -r backend/requirements-dev.lock
```

Настройки читаются из env. `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` собираются в PostgreSQL URL с драйвером psycopg; полный `DATABASE_URL` имеет приоритет. Для локального запуска вне Compose экспортируйте нужные переменные из своего `.env` и запустите команды из `backend/`:

```bash
conda run -n craftors-backend alembic -c alembic.ini upgrade head
conda run -n craftors-backend python -m app.seed
conda run -n craftors-backend uvicorn app.main:app --host 127.0.0.1 --port 8000
```

`POST /auth/login` принимает JSON с `login` и `password`, возвращает `access_token`, `token_type=bearer` и `expires_in`. Передавайте токен в `Authorization: Bearer <token>` для `GET /auth/me`; ответ содержит только `id`, `login`, `role`, `full_name`, `position`. JWT подписан HS256, содержит `sub`, `iss`, `aud`, `iat`, `nbf`, `exp`, `jti`, живёт 60 минут по умолчанию (`JWT_TTL_MINUTES`, максимум 480). Роль берётся из текущей записи пользователя в БД, а не из JWT. `/health`, `/ready` и локальный `/docs` остаются публичными.

## Клиентские заявки

Все маршруты ниже требуют `CLIENT`. `GET /me/companies` возвращает компании клиента из БД; `GET /products` показывает два демонстрационных продукта и их лимиты. `POST /applications` создаёт черновик и требует заголовок `Idempotency-Key` (1–128 символов: буквы, цифры, `.`, `_`, `~`, `-`). Тело: `company_id`, `product_code`, `amount` (целые рубли), `term_months`, `purpose`, необязательный `purpose_details`. Для инвестиционного кредита нужно указать `investment_object`, а от 5 млн ₽ — `collateral_type` и положительный `collateral_value`. Неполный черновик допускается, чтобы `submit` вернул статус `needs_info` с конкретным запросом; одобрения без этих сведений не будет. Пределы суммы и срока берутся из каталога. Условия и пороги — только демонстрационные допущения из `docs/00_common.md`, не тарифы банка.

`GET /applications` и `GET /applications/{id}` дают текущие данные только по своим компаниям. `PATCH /applications/{id}` изменяет клиентские поля только у черновика; `POST /applications/{id}/submit` запускает синхронный конвейер и возвращает фактический итоговый статус. Стоп-фактор ведёт `checking → rejected`, неполные сведения — `checking → needs_info`; остальные исходы проходят через `scoring → decision`. `GET /applications/{id}/offers` возвращает только условия предложения без PD, причин скоринга и сырого payload моков. `POST /applications/{id}/withdraw` переводит заявку в `closed` только из `draft`, `needs_info`, `manual_review`, `approved` или `counter_offer` согласно FSM. Отзыв из `manual_review` убирает заявку из очереди ручного рассмотрения, сохраняя историю и аудит; действия сотрудника после успешного отзыва возвращают 409. `GET /applications/{id}/history` возвращает фактические события с временем, ролью и ID инициатора, причиной и порядковым номером. Событие создания черновика имеет `from_status=null`. Списки заявок и событий принимают `limit` (1–100) и `offset` (0–1 000 000); для полной истории последовательно запрашивайте страницы. При `needs_info` ответ заявки содержит `info_request`.

Повтор `POST /applications` с тем же ключом и исходным телом возвращает текущую заявку с HTTP 200, даже если её позже отредактировали; первая попытка возвращает 201. Тот же ключ с другим телом возвращает 409. Чужая компания или заявка даёт 404, запрещённый переход — 409, неверные поля — 422. Статус, история и аудит перехода сохраняются в одной транзакции; конкурентные изменения защищены версией заявки. Детальные схемы запросов и ответов доступны в `/docs`.

При `needs_info` владелец вызывает `POST /applications/{id}/additional-info` с текущим `version` и хотя бы одним из полей `message`, `purpose_details`, `investment_object`, `collateral_type`, `collateral_value`. Сервис сохраняет новый снимок, выполняет `needs_info → checking` и повторно запускает проверки и решение. Устаревшая версия и повторный запрос возвращают 409; предыдущие снимки, проверки и события сохраняются.

## Ручное рассмотрение

`GET /staff/products` доступен только STAFF и возвращает действующие продукты из общего каталога, их лимиты суммы и срока, маржу, текущий демонстрационный `KEY_RATE` (по умолчанию `14.00`), надбавки групп риска A–D и правило `key_rate + margin_pp + risk_premium_pp`. `POST /staff/loan-preview` принимает `application_id`, `product_code`, целую сумму в рублях `amount` и срок `term_months`. Заявка должна быть отправлена; предварительная оценка использует её последний сохранённый снимок компании, проверки и действующий адаптер `Scorer`. Цель, полнота данных и лимиты продукта проверяются на сервере. Ответ содержит `snapshot_id`, `snapshot_version`, оценённые условия, `risk_band`, `pd`, версию/источник скоринга, ставку, платёж, `dscr`, общую сумму выплат, переплату, лимиты и признаки `indicative=true`, `demonstration=true`. Категория риска вычисляется скорером, а не задаётся сотрудником. Недопустимые условия дают 422; недоступная оценка — 503 без кредитного решения. Расчёт ориентировочный, не создаёт `Score`, `Decision` или `Offer`, не меняет заявку и `status_events`; в аудит записывается только факт успешного расчёта. При окончательном ручном решении условия и скоринг проверяются заново.

`GET /staff/applications` показывает любому авторизованному STAFF все отправленные заявки, включая автоматические решения и завершённые заявки; черновики и закрытые до отправки заявки скрыты. Доступны фильтр `status`, `limit` и `offset`. Просмотр списка и карточки `GET /staff/applications/{id}` записывается в аудит. Карточка содержит профиль компании, последние проверки DATA/FNS/BKI, демонстрационную PD и причины скоринга, предложения, историю, `decisions` (источник `created_by`, основание) и `comments` (внутренние заметки). Массив `dscr` указывает `scope` (`original_application` либо `offer`), `offer_id`, `snapshot_version`, `product_code`, сумму, срок, ставку, значение и пояснение. Расчёт использует финансовый снимок соответствующего решения и записанную ставку предложения. Ставка исходной оценки восстанавливается только при наличии автоматического предложения по тому же продукту и сохранённых оценок; иначе значение равно `null` с пояснением. `GET /staff/audit?application_id={id}` показывает журнал по любой отправленной заявке; без фильтра — по всем отправленным. Записи решений и внутренних заметок дополнены полями `decision_source` и `internal_comment` в STAFF-ответе; текст заметок не хранится в `audit_events.details`.

`GET /staff/applications/{id}/comments` возвращает внутренние заметки STAFF по отправленной заявке в порядке создания (`limit` 1–100, `offset` 0–1 000 000). `POST` по тому же пути принимает `{"body":"..."}` (1–2000 символов после удаления пробелов по краям) и возвращает созданную запись с `id`, `application_id`, `author_user_id`, `body`, `created_at` (201). Читать и добавлять заметки может любой STAFF с правом просмотра заявки; клиентские черновики скрыты. Записи хранятся в `staff_comments` отдельно от аудита и `status_events`; создание и просмотр аудируются без текста заметки. Заметка не меняет статус и не отправляется клиенту. Для запроса сведений у клиента используется только `request-info`.

Из `manual_review` только назначенный сотрудник вызывает `POST /staff/applications/{id}/decision` с `decision` (`approve`, `counter`, `reject`) и обязательным внутренним `comment`. Для `counter` можно указать `amount`, `term_months` и/или `product_code`; сервис заново проверяет лимиты продукта, цель кредита, обязательные сведения и скоринг. `POST /staff/applications/{id}/request-info` принимает обязательные `fields` (список из `purpose_details`, `investment_object`, `collateral_type`, `collateral_value`, с учётом продукта) и внутренний `comment`. Публичное `info_request` формируется по шаблонам полей; клиент отвечает через `additional-info`. Внутренний комментарий сохраняется отдельно в `staff_comments`. Решения, условия, переходы и аудит сохраняются одной транзакцией. Чужое назначение даёт 404, недопустимый переход — 409. Клиентские ответы не содержат PD, DSCR, внутренних комментариев, причин скоринга и сырых данных ФНС/БКИ.

## Принятие предложения и демо-выдача

Для frontend STAFF журнал `GET /staff/audit?application_id={id}` возвращает дополнительно `status_at_event` (состояние именно на момент записи), `actor_display_name`, `company_name`, `decision_id`, `status_event_id`, `comment_id`, `comment_author_user_id`, `comment_created_at`, `offer_id` и `offer_terms` (`product_code`, `amount`, `term_months`, `rate`, `monthly_payment`). У старых событий без соответствующего объекта связь может быть `null`. Условия в `offer_terms` берутся из Offer данного события; его последующий статус на них не влияет. В карточке у ручного решения есть `internal_comment`, а у заметок — `audit_event_id` и, для request-info, `status_event_id`. Для демо-подписания неверный код возвращает `INVALID_CODE` (422), исчерпание попыток — `CODE_ATTEMPTS_EXCEEDED` (429); секрет кода в ошибке отсутствует.

Клиент получает реквизиты без повторного ввода через `GET /me/companies/{id}/requisites`. Для конкретного доступного предложения доступны `GET /offers/{id}/contract` (JSON), `GET /offers/{id}/contract.pdf` (PDF с графиком) и `GET /offers/{id}/schedule` (таблица JSON). Сотрудник видит документы только назначенной заявки; чужие ресурсы дают 404. После принятия условия из `Offer`, реквизиты и график фиксируются в `credit_contracts` одной транзакцией со статусом и аудитом. Повторный просмотр берёт сохранённый снимок. Для старых принятых предложений без снимка он создаётся при первом просмотре из исторических условий `Offer` и текущих реквизитов профиля.

Плановая дата первого платежа — день принятия плюс календарный месяц с переносом на последний день месяца при необходимости. Следующие даты отсчитываются от числа первой плановой даты по тому же правилу. Предварительный просмотр использует текущую дату UTC, после принятия даты фиксируются. Суммы — целые рубли, проценты округляются `ROUND_HALF_UP`, последний платёж полностью закрывает основной долг. PDF формируется локально библиотекой ReportLab со шрифтом Noto Sans; лицензия шрифта находится в `app/assets/LICENSE.txt`. Для локального запуска установите `KEY_RATE=14.00`; старые предложения не пересчитываются.


Владелец принимает актуальное предложение со статусом `proposed` через `POST /offers/{id}/accept` либо отклоняет через `POST /offers/{id}/decline`. Принятие переводит заявку из `approved` или `counter_offer` в `accepted`; отклонение закрывает её. Повторные и устаревшие операции дают 409. Состояние предложения, заявки, история и аудит сохраняются в одной транзакции.

После принятия `POST /applications/{id}/sign-demo/code` возвращает одноразовый шестизначный код и время окончания действия. Это **допущение MVP**: код показывается непосредственно в защищённом ответе API, без SMS и внешнего канала. Ответ имеет `Cache-Control: no-store`. В БД хранится только HMAC-SHA256 от кода, связанный с заявкой; ключ берётся из `JWT_SECRET`, сам код не попадает в аудит или историю. Код действует 5 минут, повторная выдача в этот период ограничена, после пяти неверных попыток код блокируется до окончания срока. `POST /applications/{id}/sign-demo` с телом `{"code":"123456"}` при верном коде сохраняет реальные переходы `accepted → signed_demo → disbursed_demo`. Поле `status_label` в клиентском ответе показывает итог «Кредит выдан (демо)». Повторная подпись не создаёт вторую выдачу. Демонстрационный договор не имеет юридической силы; проводок и денежных переводов нет.

**Допущение MVP:** лимит входа хранится в памяти процесса: 5 попыток в минуту на логин (включая попытки с разных IP) и на пару логин/IP, 30 на IP. При нескольких репликах лимит не общий; до публичного масштабирования нужен общий лимитер, а также механизм отзыва уже выданных JWT. Приложение не принимает cookie для авторизации. Ответы об ошибках входа не сообщают, существует ли логин.

Ревизия `0002_credit_schema` создаёт `users`, `companies`, `products`, `applications`, `application_snapshots`, `check_results`, `scores`, `decisions`, `offers`, `status_events` и `audit_events`. Ревизия `0003_staff_assignment` добавляет назначение сотрудника к заявке и назначает существующие заявки `manual_review` активному `staff1`, если он есть. Ревизия `0004_sign_code_attempts` сохраняет счётчик попыток демо-подписания. Ревизия `0005_contracts` добавляет реквизиты и снимки договоров без удаления существующих строк. Ревизия `0006_staff_comments` создаёт отдельные внутренние комментарии STAFF. Миграции не создают демо-данных. `companies.owner_user_id` связывает компанию с владельцем; клиентский API проверяет роль и принадлежность для каждого обращения. Снимки, результаты проверок, оценки, решения и события хранятся отдельными записями без каскадного удаления. FSM и фильтрация содержимого аудита выполняются сервисами, а не ограничениями схемы.

Текущую ревизию показывает `conda run -n craftors-backend alembic -c alembic.ini current`. Откат `alembic downgrade 0001_initial_empty` удаляет прикладные таблицы и допустим только на одноразовой тестовой БД; перед изменениями долговременной БД нужна резервная копия.

Без работающей БД `/health` остаётся доступным, а `/ready` возвращает 503. Текущий локальный Swagger — `/docs`; публичный префикс `/api` через nginx относится к следующему этапу. В production дополнительно обязательны `APP_ENV=production`, `APP_DOCS_ENABLED=false`, явный `APP_ALLOWED_HOSTS`, непустые учётные данные БД и `JWT_SECRET`. Не публикуйте PostgreSQL наружу и не печатайте переменные с паролями, токенами или полный `DATABASE_URL`.

## Проверки

Из `backend/`:

```bash
conda run -n craftors-backend python -m pytest -q
conda run -n craftors-backend ruff check app tests alembic
conda run -n craftors-backend ruff format --check app tests alembic
conda run -n craftors-backend alembic -c alembic.ini heads
conda run -n craftors-backend alembic -c alembic.ini upgrade head --sql
conda run -n craftors-backend python -m pip check
conda run -n craftors-backend python -m pip_audit --no-deps --disable-pip -r requirements-dev.lock
```

Первая миграция создаёт только служебную таблицу `alembic_version`; вторая — прикладную схему. Проверка `--sql` не требует БД. Тесты схемы применяют и откатывают миграции на изолированной SQLite с включёнными внешними ключами; окончательная проверка PostgreSQL выполняется через Compose.

Зависимости объявлены в `pyproject.toml`; runtime и dev версии зафиксированы в `requirements.lock` и `requirements-dev.lock`. После изменения зависимостей пересобирайте оба lock-файла через `pip-compile` под Python 3.12 в `craftors-backend` и повторяйте проверки. Хеши пакетов пока не закреплены.


## Права STAFF и исторические сведения

`GET /staff/applications/{id}` возвращает назначение в
`application.assigned_staff_user_id` и верхнеуровневый `allowed_actions`:
`approve`, `counter`, `reject`, `request_info`. Список заполнен только для
активного назначенного сотрудника при `manual_review`. Это подсказка для UI;
каждый POST по-прежнему отдельно проверяет назначение и допустимый переход.
Поля назначения и прав не добавляются в клиентский контракт заявки.

Новые события `application.needs_info` сохраняют `info_request_text` как снимок
отправленного публичного текста, включая SYSTEM-запросы. Ручной
`staff.request_info` сохраняет тот же текст и `requested_fields`, отдельно от
внутреннего комментария. При переходе в `manual_review` сохраняются
`assigned_staff_user_id` и `assigned_staff_display_name` получателя назначения.
`GET /staff/audit` возвращает эти три исторических поля на верхнем уровне.
Смена текущего текста, назначения или имени не изменяет сохранённые события;
для старых событий без снимков поля остаются `null`.

Миграция `0007_normalize_staff_comments` приводит обе встречающиеся версии
`0006` к текущей модели: `body TEXT NOT NULL`, CHECK длины после trim от 1 до
2000 и индекс `(application_id, id)`. Существующие строки и внешние ключи
сохраняются. Уже применённую `0006` повторно запускать не требуется. Downgrade
этой исправляющей миграции восстанавливает исходные тип, CHECK и индекс `0006`,
сохраняя существующие строки и возможность дальнейшего отката.


## Исходный DSCR, история дополнений и клиентская предварительная ставка

В STAFF-карточке элемент `dscr` с `scope=original_application` теперь вычисляется
без Offer/Decision: текущие `KEY_RATE`, маржа продукта и надбавка сохранённой
оценки риска того же снимка и тех же продукта/суммы/срока передаются в существующие
`credit_terms`, `annuity_payment`, `dscr`. Ответ содержит `snapshot_id`,
`snapshot_version`, `score_id`, `key_rate`, `product_code`, `amount`, `term_months`,
`rate`, `monthly_payment`, `value`, `calculation_basis=current_formula`.
При недоступной оценке, продукте, ограничениях или финансовых данных `value=null`
и `explanation` указывает причину. Оценка другого снимка не используется.
Элементы `scope=offer` по-прежнему используют сохранённую ставку и финансовый
снимок соответствующего предложения (`calculation_basis=saved_offer`).
Сохранённые предложения, решения и договоры не изменяются.

CLIENT `GET /products` дополнен `indicative_rate_min`: текущий `KEY_RATE` плюс
маржа продукта и минимальная надбавка из действующей серверной формулы.
Значение передаётся в процентах годовых (например, `20.000` означает 20%). Это
минимальная демонстрационная предварительная ставка, не одобренные условия.
Категория риска, PD и внутренние факторы клиенту не передаются.

Новые ответы дополнительных сведений сохраняются внутри JSON `details` своего
события `application.checking` (CLIENT), атомарно с изменением анкеты, снимком и
обработкой. Старые значения читаются до изменения полей. STAFF-карточка содержит
`additional_info_responses` (новые сверху); соответствующая строка журнала имеет
поле `additional_info` с тем же объектом:

- `request_event_id`: ID AuditEvent запроса `application.needs_info` (либо
  явно связанного `staff.request_info` для старого формата); `null`, если связи нет;
- `response_event_id`: ID AuditEvent ответа клиента;
- `answered_at`: серверная дата и время события ответа;
- `requested_fields`: сохранённый список полей запроса либо `null`, если он неизвестен;
- `changes`: список `{field, before, after}` только фактически изменённых
  переданных полей. `message` обозначает публичный текст ответа; остальные поля:
  `purpose_details`, `investment_object`, `collateral_type`, `collateral_value`.

Системный запрос сохраняет `requested_fields` из результата проверки DATA, ручной —
из выбранных сотрудником полей. Запрос и ответ связываются по сохранённому
`status_event_id`, без сопоставления по времени. Несколько циклов сохраняются
отдельно. Старые ответы без снимка изменений не реконструируются из текущей анкеты.
Новая миграция не требуется: используется существующий JSON аудита; текущая
ревизия остаётся `0007_normalize_staff_comments`.
