# Решения и допущения (D4)

Что мы упростили, почему, чем это грозит и как развивать. В коде те же места помечены «Допущение MVP».
Открытые и принятые продуктовые решения по ходу работы (П1–П9) — в [00_index.md](00_index.md).

## Продукт и скоуп

| Решение / упрощение | Почему | Риск | Как развивать |
|---|---|---|---|
| Только действующие клиенты банка; данные компании подставляются из профиля и выписки | Кейс и главный UX-принцип: «не спрашивать то, что банк знает» | Новые клиенты не обслуживаются | Онбординг новых клиентов: ИНН → ФНС → открытие счёта → тот же конвейер |
| Два продукта — оборотный и инвестиционный; рефинансирование и овердрафт — карточки «скоро» | Must из ТЗ. У овердрафта другая логика (лимит, транши), у рефинансирования — выбор кредитов из БКИ | Узкая линейка на демо | Рефинансирование: выбор кредитов из БКИ, выгода = снижение платежа; механизм альтернативного продукта в оптимизаторе уже есть |
| Подбор — детерминированные правила по категории цели, без ML | Прозрачно и объяснимо; данных для обучения рекомендаций нет | Рекомендации не персонализированы по отрасли | Учитывать ОКВЭД и сезонность; Could — AI-помощник на открытых весах |
| Лента по ОКВЭД не делается | В брифе от 21.10 её убрали из требований к демо (вопрос организаторам — [07](07_questions_to_organizers.md)) | Если всё-таки нужна — минус к модулю 8 | Простой контентный рекомендатель: теги ОКВЭД-секции × тематика |
| Всё общение — внутри кабинета, без e-mail и SMS | Требование ТЗ | Клиент может не заметить решение | Push-уведомления и SMS в промышленной версии |

## Правила и цены

| Решение / упрощение | Почему | Риск | Как развивать |
|---|---|---|---|
| Ставка = ключевая ЦБ + маржа продукта + надбавка за группу риска; маржи +8 / +6 п.п. (П2) | Рыночность: при ключевой 14% это 22–27% и 20–25%, сопоставимо с открытыми данными банков | Ставка не учитывает срок, залог и стоимость фондирования | Ценообразование с учётом срока, залога, RAROC и стоимости фондирования |
| Пороги: PD 12% / 25%, DSCR 1,25, просрочка 30 / 90 дн., автолимит 30 млн ₽ — именованные константы | Учебное допущение MVP; понятны жюри и легко меняются | Не откалиброваны на реальном портфеле | Калибровка на исторических данных, разные пороги по сегментам и продуктам |
| Оптимизатор перебирает сумму (−10%), срок (+12 мес.) и альтернативный продукт той же цели | Даёт клиенту альтернативу вместо отказа (гипотеза H4) | Перебор грубый; альтернативный продукт при текущей линейке почти не выигрывает | Оптимизация по доходности банка; больше параметров (залог, график погашения) |
| В скорер отправляются только варианты, у которых DSCR проходит даже по минимальной ставке | Остальные недопустимы при любом PD — экономим вызовы модели | «Лучший PD» для правила 6 считается среди оценённых вариантов | Батч-скоринг всех кандидатов, когда модель быстрая |
| Комфортная сумма показывается на выбранный и на максимальный срок (П9) | Иначе подбор называет меньшую сумму, чем потом предлагает банк | — | Слайдер «сумма ↔ срок» с живым расчётом платежа |
| Клиент не видит PD, группу риска и веса; сотрудник видит всё | Понятность для клиента и защита модели от подбора параметров | Клиенту меньше прозрачности о «внутренней кухне» | Расширенное объяснение «что улучшит решение» на основе факторов |

## Данные, интеграции, скоринг

| Решение / упрощение | Почему | Риск | Как развивать |
|---|---|---|---|
| ФНС/ЕГРЮЛ/ЕГРИП, «Прозрачный бизнес», БКИ — локальные моки из JSON по ИНН | Требование автономности ТЗ | Не проверяется реальная интеграция | HTTP-клиенты к шлюзам с тем же контрактом, ретраи, таймауты и кэш |
| Финансы компании — агрегаты синтетической выписки за 12 мес. | Только синтетические данные | Нет помесячной динамики и сезонности | Расчёт по транзакциям счёта: тренды, сезонность, концентрация контрагентов |
| Скоринг за интерфейсом `Scorer`; сейчас — прозрачная скоркарта (`MockScorer`), модель ML подключается флагом `SCORER=model` | Основной сценарий не должен зависеть от модели | Веса скоркарты экспертные | Обученная CatBoost-модель с калибровкой и SHAP; мониторинг PSI и дрейфа |
| Обучение на синтетике, без отказанных заявок | Реальных данных нет | Смещение (reject inference — вне MVP), метрики не переносятся на реальность | Обучение на реальном портфеле, reject inference, регулярное переобучение |

## Техника и безопасность

| Решение / упрощение | Почему | Риск | Как развивать |
|---|---|---|---|
| Конвейер выполняется синхронно в запросе подачи | Миллисекунды на заявку; проще код и демо | Медленные интеграции заблокируют запрос | Воркер с очередью; статусы и переходы остаются теми же |
| Лимит попыток входа хранится в памяти процесса | Один экземпляр API в MVP | При нескольких экземплярах лимит обходится | Redis или ограничение на API-шлюзе |
| Подпись — 6-значный код в интерфейсе (демо-SMS), HMAC-хэш, 5 минут | Нельзя использовать SMS и реальную подпись | — (явно помечено «демо») | Простая электронная подпись через SMS-шлюз или УКЭП |
| Выдача — смена статуса `disbursed_demo` без проводок | Реальные проводки — вне скоупа | — (помечено «демо») | Интеграция с АБС, график платежей, обслуживание кредита |
| Локальный запуск без Docker — на SQLite | Docker не всегда установлен у команды | Расхождения диалектов SQLite и Postgres | Проверка в CI на Postgres (testcontainers) |
| Каталог продуктов доступен только после входа (П4) | RBAC на каждом эндпоинте | Нельзя показать каталог до входа | Публичная витрина продуктов отдельно от кабинета |
| В причинах решения сотрудника клиент видит «Комментарий специалиста» без ФИО (П8) | Не раскрывать персональные данные сотрудника | — | Подпись «Ваш менеджер» и чат с банком внутри кабинета |
