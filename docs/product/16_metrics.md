# Продуктовые метрики

Все метрики считаются по двум журналам, которые конвейер уже пишет. Отдельной аналитики не нужно.
- **`status_events`** — каждый переход статуса: `application_id, from_status, to_status, actor_role (CLIENT | SYSTEM | STAFF), actor_id, comment, created_at`.
- **`audit_events`** — значимые действия: `action` (`application.submit`, `application.auto_decision`, `staff.view`, `staff.decision`, `staff.request_info`, `offer.accept`, …), `actor_role, actor_id, application_id, details, created_at`.

Эталонная реализация — [metrics.py](metrics.py). Формулы ниже совпадают с ней, проверено на базе backend команды (26.10.2026).
```bash
pip install sqlalchemy "psycopg[binary]"
python docs/product/metrics.py postgresql+psycopg://<пользователь>:<пароль>@localhost:5432/credit_cabinet
```

## Определения

«Поданная заявка» — заявка, у которой есть событие `to_status = submitted` (черновики не считаем).
«Статусы решения» — `approved, counter_offer, rejected, manual_review, needs_info`; «финальные» — `approved, counter_offer, rejected`.

| # | Метрика | Формула по журналам | Цель MVP | Что показывает / что делать, если плохо |
|---|---|---|---|---|
| 1 | **Time-to-decision** (автоматические решения) | Для каждой поданной заявки: `t(первое событие со статусом решения, actor = SYSTEM) − t(событие submitted)`. Считаем медиану и p95 | p95 < 1 мин | Скорость — ключевое ожидание рынка (ВТБ — «около 5 минут», Сбер — «от 1 минуты»). Если растёт — смотреть скорость скорера и число вариантов оптимизатора |
| 2 | **Доля автоматических решений** | Среди заявок с финальным статусом: доля тех, у кого первый финальный статус выставил `SYSTEM` и в истории нет `manual_review` | ≥ 70% | Нагрузка на аналитиков. Если падает — пересмотреть флаги правила 3 и порог правила 6 |
| 3 | **Число полей, которые вводит клиент** | Не из журналов: число обязательных полей анкеты по продукту из [справочника полей](03_fields.md). Дополнительно по `audit_events.action = application.update` → `details.fields` видно, какие поля клиенты правят чаще всего | ≤ 6 | Принцип «не спрашивать то, что банк знает». Сейчас: оборотный 3, инвестиционный до 5 млн 4, от 5 млн 6 |
| 4а | **Конверсия «оффер → принят»** | Заявки с переходом в `accepted` / заявки, у которых был `approved` или `counter_offer` | растёт от релиза к релизу | Насколько условия устраивают клиента |
| 4б | **Конверсия «встречное → принято»** | Заявки с событием `from_status = counter_offer → to_status = accepted` / заявки со статусом `counter_offer` | растёт; ориентир — не ниже 4а | Проверка гипотезы H4: «вместо отказа — альтернатива». Если низкая — менять тексты встречного или шаги оптимизатора |
| 5 | **Доля заявок с запросом сведений** | Заявки, где был `to_status = needs_info` / поданные заявки. Отдельно: `actor = SYSTEM` (не хватило данных по правилу 2) и `actor = STAFF` (запрос аналитика) | ≤ 15% | Сигнал качества анкеты. Высокая системная доля — анкета плохо подсказывает, что нужен залог или объект; высокая доля от сотрудника — данных из банка мало для решения |
| 6 | **Время сотрудника на ручную заявку** | Для заявок с `manual_review`: `t(первое staff.decision или staff.request_info) − t(первое staff.view после входа в manual_review)` по `audit_events`. Медиана | < 5 мин | Эффективность кабинета сотрудника («вся картина на одном экране»). Если растёт — смотреть, каких данных не хватает в карточке |

Дополнительно, из тех же журналов:
- **Time-to-cash** — `t(disbursed_demo) − t(submitted)`: полное время до денег, включая действия клиента.
- **Воронка** — поданные → решение → оффер → принято → подписано → выдано (по первым событиям каждого статуса).
- **Время в очереди** — `t(первое staff.view) − t(manual_review)`: как быстро аналитик берёт заявку.

|---|---|---|---|
| Time-to-decision (авто), медиана / p95 | 0 мс / 0 мс (n=8) | < 60 с | ✓ |
| Доля автоматических решений | 86% (6/7) | ≥ 70% | ✓ |
| Полей вводит клиент (обязательных) | Оборотный: 3, Инвестиционный до 5 млн ₽: 4, от 5 млн ₽: 6 | ≤ 6 | ✓ |

| Конверсия «встречное → принято» | 0% (0/2) | растёт | — |
| Доля заявок с запросом сведений | 12% (1/8; система 1, сотрудник 0) | ≤ 15% | ✓ |
| Время сотрудника на ручную заявку, медиана | 0 мс (n=1) | < 5 мин | ✓ |

Как читать:
- **Time-to-decision ≈ 0 мс по журналу** — весь конвейер пишет события в одной транзакции; полное время ответа API на подачу — 0,09 с (smoke TC-01).
- **Конверсии и время сотрудника** на скриптовых данных не показательны. Реальные значения — после демо с людьми.

## Как развивать

1. Вывести метрики 1, 2, 5, 6 в кабинет сотрудника (рядом с журналом действий) или в отдельный дашборд руководителя.
2. Для Time-to-decision в промышленной версии добавить в `status_events` время начала обработки воркером.
3. Для конверсий добавить в аудит событие «клиент открыл оффер», чтобы отличать «не видел» от «видел и не принял».
