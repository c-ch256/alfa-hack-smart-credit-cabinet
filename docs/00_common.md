# ОБЩИЙ КОНТЕКСТ ПРОЕКТА (одинаковый для всех ролей)

Ты работаешь в команде хакатона **Альфа-Хак 2026**, кейс **«Умный кредитный кабинет предпринимателя»**. Команда — 4 человека: Product/UX/Business analyst, Backend, Frontend, ML. Срок — **4 дня**. Ниже — общие договорённости. Они обязательны для всех ролей: если твоё решение им противоречит, сначала скажи об этом, а не меняй контракт молча.

## 1. Суть кейса
Прототип **цифрового кредитного конвейера** для малого и микробизнеса. Он соединяет:
- **путь клиента**: потребность в деньгах → подбор продукта → заявка → решение → принятие предложения → подписание → выдача (имитация);
- **обработку в банке**: проверка полноты → обогащение из внешних источников (моки ФНС/БКИ) → ML-скоринг → кредитная политика и оптимизация условий → автоматическое или ручное решение → аудит.

Обе стороны работают с **одной заявкой и одними данными**. Статус меняется последовательно, история сохраняется, повторного ввода нет.

## 2. Пользователи
- **CLIENT** — действующий клиент банка, ИП или ООО (собственник, директор, бухгалтер, уполномоченный сотрудник). Банковской экспертизы нет. Регистрация нового бизнеса и физлица без бизнеса — вне кейса.
- **STAFF** — кредитный аналитик банка: разбирает пограничные заявки, запрашивает сведения, принимает и обосновывает решение.
- Один веб-интерфейс, две роли, тестовые учётки.

## 3. Жёсткие ограничения из ТЗ (нарушать нельзя)
1. Только **веб-интерфейс** (мобильное приложение запрещено). Достаточно качественной десктопной версии.
2. **Автономность**: никаких систем Альфа-Банка. ФНС/ЕГРЮЛ/ЕГРИП, «Прозрачный бизнес», БКИ, подписание и выдача — **локальные моки и демонстрационная имитация**, явно помеченные в коде и в `THIRD_PARTY_NOTICES`; реальные операции не выполняются.
3. Только **синтетические данные**.
4. **Никаких платных** API, подписок и закрытых лицензий в проверяемой версии.
5. Весь сценарий — **внутри продукта**: без e-mail, внешних SMS, мессенджеров и звонков. Код демо-подписания показываем только в интерфейсе.
6. LLM, OCR и любые модели — **только с открытыми весами** (ориентир ≤ 120B). LLM подключается через **OpenAI-совместимый API** с переменными `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`. Без модели основной сценарий обязан работать.
7. Запуск одной командой `docker compose up --build` на обычном ПК (~12 ГБ RAM, **без GPU**, интернет есть) обязателен к готовности MVP; публичное размещение желательно.
8. Код в GitHub с историей коммитов, тег или commit hash на момент дедлайна. Доступ для жюри: `alfa-hack-2026`.
9. Обязательные материалы: `README.md`, `.env.example`, `THIRD_PARTY_NOTICES`, архитектурная схема, описание API + OpenAPI, коллекция запросов, диаграмма состояний заявки, модель данных, тест-сценарии, синтетические данные и тестовые учётки.
10. Версии зафиксированы lock-файлами.

## 4. Как оценивают (на это работаем)
Целостность сквозного процесса · UX для клиента **и** банка · согласованность модулей (данные переиспользуются, статусы последовательны) · enterprise-подход (безопасность, надёжность, сопровождаемость) · обоснованность решений и потенциал развития · готовность к самостоятельной проверке жюри.

## 6. Продукты (демонстрационные допущения MVP, не тарифы и не политика банка)
| code | Название | Сумма | Срок | Маржа | Особенности |
|---|---|---|---|---|---|
| `working_capital` | Оборотный кредит | 300 тыс – 30 млн ₽ | 3–36 мес. | +4,0 п.п. | Цели: закупка, поставщики, аренда, исполнение контракта |
| `investment` | Инвестиционный кредит | 1–100 млн ₽ | 12–84 мес. | +3,0 п.п. | Обязателен объект инвестиций; от 5 млн ₽ — залог (вид и стоимость) |
| `refinance` | Рефинансирование (Could) | 500 тыс – 50 млн ₽ | 12–60 мес. | +3,5 п.п. | Клиент выбирает кредиты из данных БКИ; выгода = снижение платежа |
| `overdraft` | Овердрафт (Could) | лимит 100 тыс – 10 млн ₽ | до 12 мес. | +5,0 п.п. | В MVP — карточка «скоро» |

**Демонстрационное допущение MVP:** базовая ставка `KEY_RATE=14.00` годовых по умолчанию; расчётная ставка = заданное в `.env` значение `KEY_RATE` + маржа продукта + надбавка за группу риска (A +0; B +1,5; C +3; D +5 п.п.). Это учебные условия, не тарифы Альфа-Банка и не подключение к ЦБ. Платёж — аннуитетный, формула одна на бэке и фронте:
`payment = amount · r / (1 − (1 + r)^−n)`, где `r = rate / 12 / 100`, `n` — срок в месяцах. Деньги — **целые рубли**. Для группы A это 18% по оборотному и 17% по инвестиционному кредиту. Изменение `KEY_RATE` действует только для новых предложений; ранее созданные предложения и договоры сохраняют записанную ставку.

## 7. Главный UX-принцип: не спрашивать то, что банк уже знает
Клиент действующий, поэтому данные компании **подставляются** и показываются блоком «Данные из банка — вводить не нужно»:
- профиль + мок ФНС: ИНН, ОПФ, ОКВЭД, отрасль, регион, дата регистрации;
- синтетическая выписка по счёту за 12 мес.: средняя выручка, расходы, динамика выручки за 6 мес., текущие платежи по кредитам;
- мок БКИ: число кредитов, просрочки, долг.

Клиент вводит только: **цель, комментарий, сумму, срок**, при необходимости **объект инвестиций и залог** (для рефинансирования — выбор кредитов). Каждое поле обязано влиять на процесс.

## 8. Статусная модель заявки (backend — единственный источник правды)
Статусы: `draft, submitted, checking, scoring, decision, needs_info, manual_review, approved, counter_offer, accepted, signed_demo, disbursed_demo, rejected, closed`.

| Кто | Переходы |
|---|---|
| CLIENT | draft→submitted · draft→closed · needs_info→checking (дослал сведения) · needs_info→closed · manual_review→closed (отзыв заявки) · approved→accepted · approved→closed · counter_offer→accepted · counter_offer→closed · accepted→signed_demo |
| SYSTEM | submitted→checking · checking→scoring · checking→needs_info · checking→rejected (стоп-фактор) · scoring→decision · decision→{approved, counter_offer, manual_review, rejected} · signed_demo→disbursed_demo |
| STAFF | manual_review→{approved, counter_offer, rejected, needs_info} |

Терминальные: `disbursed_demo, rejected, closed`. Недопустимый переход → **409**. Backend сохраняет каждый фактически совершённый переход в `status_events`.
Клиенту показываем текущий статус и историю фактических переходов; пять этапов **Заявка → Рассмотрение → Решение → Подписание → Выдача** служат только группировкой уже состоявшихся событий, без фиктивной анимации. `checking/scoring/decision` для клиента — «На рассмотрении».

## 9. Логика решения: скоринг ≠ решение
- **Скоринг (mock, затем ML)** оценивает риск дефолта: `{pd, risk_band, reasons, model_version}`. Решения о кредите он не принимает. `pd` здесь — оценка риска, а бинарный класс для ML-задачи не заменяет её и не является решением.
- **Кредитная политика + оптимизатор** решают, что делать. Правила сверху вниз, срабатывает первое:
  1. **Стоп-факторы → REJECT** (на этапе checking): ФНС-статус ≠ `active`; просрочка > 90 дн.; дефолт в истории БКИ.
  2. **Неполные данные → NEEDS_INFO** (на этапе checking): нет объекта инвестиций; нет залога при сумме ≥ порога; для рефинансирования не выбраны кредиты. Клиент получает конкретный список, что дослать.
  3. **Флаги ручной проверки → MANUAL_REVIEW**: просрочка 31–90 дн.; сумма выше лимита автоодобрения (30 млн ₽).
  4. **Запрошенные условия**: если `PD < 12%` и `DSCR ≥ 1,25` → **APPROVE**.
     `DSCR = (выручка − расходы) / (текущие платежи + новый платёж)`.
  5. **Оптимизация → COUNTER_OFFER**: перебираем варианты (сумма вниз шагом 10% до минимума продукта; срок до максимума; альтернативный продукт той же цели), для каждого считаем PD через скорер и DSCR. Выбираем допустимый вариант (`PD < 12%`, `DSCR ≥ 1,25`) с максимальной суммой; при равенстве — с меньшим платежом. Сумма округляется вниз до 10 000 ₽.
  6. Допустимого варианта нет: если лучший `PD < 25%` → **MANUAL_REVIEW**, иначе → **REJECT**.
- Все перечисленные стоп-факторы, пороги и лимиты — именованные константы с пометкой «демонстрационное допущение MVP»; это не реальные кредитные правила Альфа-Банка. Низкорисковые заявки могут получать автоматическое решение по этим версионированным правилам, пограничные передаются сотруднику.
- Группы риска: A < 5% · B 5–10% · C 10–20% · D ≥ 20%.
- Клиент **не видит PD и веса**, только понятные причины и факторы. Сотрудник видит всё.

## 10. Контракт скоринга (ML ↔ Backend) — заморозить в конце дня 1
Python-интерфейс в backend: `Scorer.score(req: ScoringRequest) -> ScoringResult`. Реализации: `MockScorer` (прозрачная скоркарта) и `ModelScorer` (артефакт ML). Выбор — `SCORER=mock|model`, путь — `MODEL_DIR`.

```json
// ScoringRequest
{
  "product_code": "working_capital",
  "amount": 3000000,
  "term_months": 24,
  "collateral_value": 0,
  "company": {
    "legal_form": "OOO", "okved": "47.11", "region": "Москва",
    "business_age_months": 127, "bank_client_months": 89,
    "avg_monthly_revenue": 4200000, "avg_monthly_expenses": 3300000,
    "revenue_trend_6m": 0.04, "existing_monthly_payments": 120000
  },
  "bki": { "active_loans": 1, "max_overdue_days_12m": 0, "total_debt": 1200000, "defaults": 0 },
  "fns": { "status": "active", "tax_debt": false, "mass_address": false }
}
// ScoringResult
{
  "pd": 0.031,
  "risk_band": "A",
  "model_version": "catboost-1.0.0",
  "reasons": [
    { "feature": "max_overdue_days_12m", "text": "Нет просрочек за 12 месяцев", "effect": "decreases_risk", "contribution": -0.42 }
  ]
}
```
Производные признаки (DSCR, новый платёж, кредит к годовой выручке, покрытие залогом) скорер считает **сам** из запроса — одинаково при обучении и инференсе. Требование к скорости: ≤ 20 мс на вызов, чтобы оптимизатор успевал перебрать ~30 вариантов.

## 11. API-контракт (будущий публичный префикс `/api`) — заморозить в конце дня 1
Сейчас FastAPI предоставляет `GET /health` и Swagger `/docs` напрямую. Будущий nginx публикует прикладные маршруты с префиксом `/api` (например, `/api/health` и `/api/docs` через прокси); внутренние пути FastAPI `/health` и `/docs` сохраняются. Для публичного Swagger нужно согласовать проксирование OpenAPI и `root_path`, чтобы страница загружала схему через `/api`.
- **Auth**: `POST /auth/login` · `GET /auth/me`
- **Каталог и подбор**: `GET /products` · `GET /me/companies` · `POST /recommendations` `{company_id, purpose_category, amount, term_months}` → продукты по убыванию соответствия: причины, ориентир ставки и платежа, предварительная нагрузка, подсказка суммы
- **Заявки клиента**: `GET /applications` · `POST /applications` (заголовок `Idempotency-Key`) · `GET /applications/{id}` · `GET /applications/{id}/history` · `PATCH /applications/{id}` (только draft, иначе 409) · `POST /applications/{id}/submit` · `POST /applications/{id}/additional-info` · `POST /applications/{id}/withdraw`
- **Предложения и подписание**: `GET /applications/{id}/offers` · `POST /offers/{id}/accept` · `POST /offers/{id}/decline` · `POST /applications/{id}/sign-demo/code` · `POST /applications/{id}/sign-demo` `{code}`
- **Сотрудник**: `GET /staff/products` · `POST /staff/loan-preview` `{application_id, product_code, amount, term_months}` (ориентировочный расчёт по сохранённому снимку) · `GET /staff/applications?status=` · `GET /staff/applications/{id}` · `GET|POST /staff/applications/{id}/comments` (внутренние заметки только STAFF, без изменения статуса) · `POST /staff/applications/{id}/decision` `{decision: approve|counter|reject, amount?, term_months?, product_code?, comment}` (комментарий обязателен) · `POST /staff/applications/{id}/request-info` `{fields, comment}` (поля анкеты и внутреннее основание; публичный текст по шаблонам) · `GET /staff/audit?application_id=`. Просмотр и журнал доступны для всех отправленных заявок; ручные действия только назначенному сотруднику из `manual_review`.
- **Could**: `POST /assistant/chat`
- **Система**: `GET /health`
- **Ошибки**: 401 — нет или просрочен токен; 403 — не та роль; **404 — чужая заявка или компания** (не раскрываем существование); 409 — недопустимый переход; 422 — валидация с понятным текстом на русском; 429 — лимит попыток входа. Формат: `{"detail": "...", "code": "..."}`.
- Поля — `snake_case`, даты — ISO 8601 UTC, деньги — целые рубли.

## 12. Модель данных
`users` (login, password_hash, role, full_name, position) → `companies` (профиль + агрегаты выписки) → `applications` (number, product_code, status, amount, term_months, purpose, purpose_details, investment_object, collateral_type, collateral_value, info_request, info_response, idempotency_key, sign_code_hash, sign_code_expires_at, timestamps) → `check_results` (DATA | FNS | BKI; ok | warn | fail; summary; payload) · `scores` (pd, risk_band, model_version, reasons, features) · `offers` (kind: original | counter | alternative_product; product_code, amount, term_months, rate, monthly_payment; status: proposed | accepted | declined | superseded; created_by: SYSTEM | STAFF) · `status_events` · `audit_events` (actor, action, application_id, details — включая просмотр карточки сотрудником) · `staff_comments` (заявка, сотрудник, текст, время; только внутреннее чтение STAFF). Could: `refinance_items`.
