# Модель угроз MVP «Умный кредитный кабинет»

Статус: проект до разработки. Охват: React-клиент, FastAPI, PostgreSQL, детерминированный mock scoring и будущий ML-адаптер, моки ФНС/БКИ, контейнеры и процесс сборки. Данные и интеграции только синтетические, однако права доступа и финансовые решения проектируются как для чувствительной системы. Ориентиры: [OWASP API Security Top 10 (2023)](https://api-security.owasp.org/editions/2023/en/0x11-t10/), [OWASP ASVS](https://asvs.owasp.org/) и [NIST SSDF SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final). Их использование не означает подтверждённого соответствия.

## Активы, доверительные границы и допущения

Защищаем: учётные записи и сессии, сведения о заявках и организациях, результаты моков, снимки признаков, версии модели и правил, решения сотрудников, журнал статусов и аудит, конфигурацию и секреты. Основные нарушители: внешний пользователь, клиент другой организации, сотрудник вне разрешённой очереди, скомпрометированная учётная запись, вредоносная зависимость и оператор с ошибочной конфигурацией.

Границы доверия: браузер → API; API → БД; домен заявок → моки/адаптер скоринга/правила; сотрудник → окончательное решение; сборка/контейнер → среда исполнения. Любые поля из браузера и ответы моков считаются недоверенными. Моки являются локальными демонстрационными адаптерами, но их контракт и ошибки обрабатываются как у внешнего источника. Backend отвечает за авторизацию, хранилище, моки интеграций, решения и аудит; отдельный ML-участник отвечает за синтетические обучающие данные, обучение, валидацию и версии настоящей модели. Реальные требования банка к хранению, срокам хранения и полномочиям неизвестны и подлежат отдельному согласованию.

## Угрозы, защита и проверка

| Область / OWASP API 2023 | Угроза | Меры защиты | Проверка |
| --- | --- | --- | --- |
| API1 BOLA | Подмена `application_id` открывает заявку другой организации | Проверка владения/назначения на сервере для чтения, изменения, событий, вложенных ресурсов и экспорта; фильтрация запросов по разрешённой области | Интеграционные тесты: клиент A не читает/меняет B; сотрудник вне назначения не читает B; ответы без содержимого объекта |
| API2 Broken Authentication | Подбор пароля, угон/повтор сессии | Надёжный хеш паролей, короткоживущая сессия, защищённые cookie `HttpOnly`, `Secure`, `SameSite` и CSRF-защита при cookie-авторизации; лимит попыток входа; отзыв сессии | Тесты неверных/истёкших/отозванных сессий, CSRF, лимитов; ревизия конфигурации cookie |
| API3 Broken Object Property Level Authorization | Подмена роли, статуса, решения, суммы или организации через массовое присваивание | Отдельные схемы ввода/вывода по роли и операции; allowlist изменяемых полей; сервер создаёт служебные поля | Тесты с лишними и запрещёнными полями, проверка, что они отвергнуты и запись не изменилась |
| API4 Unrestricted Resource Consumption | Массовая отправка заявок/оценок перегружает БД или модель | Ограничение размера тела, пагинация и лимиты, rate limit на вход и дорогие операции, таймауты моков/скоринга, ограниченные повторы и очередь задач | Нагрузочные тесты верхних границ и тесты таймаута/повтора без дублей |

| API6 Unrestricted Access to Sensitive Business Flows | Автоматизация подачи и решений, повтор операции | Идемпотентный ключ подачи/решения, лимиты, подтверждение полномочий сотрудника, неизменяемый след действий, контроль переходов | Параллельные и повторные запросы создают ровно один допустимый переход/итог |
| API7 SSRF | URL из заявки заставляет сервер обратиться к внутренним ресурсам | Моки с фиксированными адресами/локальными интерфейсами; запрет произвольных URL и исходящих запросов из пользовательских полей | Тесты URL-полей и конфигурации egress; попытки внутренних адресов отклоняются |
| API8 Security Misconfiguration | Отладочные настройки, открытые CORS, секреты в образе, публичная БД | Разные настройки dev/demo, явный CORS allowlist, отключённый debug, непубличная БД, healthcheck без секретов, минимальные права контейнера | Проверка образа и Compose-конфигурации, скан секретов, smoke-тест без debug endpoints |
| API9 Improper Inventory Management | Скрытые тестовые/устаревшие API сохраняют доступ | Версионированный OpenAPI, единый перечень маршрутов, закрытие/удаление экспериментальных endpoints, контроль окружений | Сравнение реальных маршрутов с OpenAPI и ревизия перед демонстрацией |

### Финансовые данные и целостность решений

- Минимизировать собираемые поля; использовать только синтетические идентификаторы и значения. В логи, исключения и телеметрию не писать полные анкеты, токены, признаки или результаты моков. В ответах API выдавать ровно поля, нужные роли.
- TLS нужен на границе демонстрационного развёртывания; БД недоступна извне. Секреты и ключи хранятся вне Git и образов, права БД ограничены. Шифрование хранения и срок удаления данных должны быть определены до работы с любыми реальными сведениями.
- Ввод сумм и сроков валидируется по типу и диапазонам демонстрационного продукта; денежные значения хранятся как decimal с валютой. Используются параметризованные запросы ORM, безопасный вывод React и ограничения на формат текстовых полей.
- Каждый запуск оценки ссылается на неизменный снимок заявки и ответов моков, версию схемы признаков, адаптера скоринга и правил. Ответ скоринга помечает `mock`/`model` и тестовый характер результата; бинарный прогноз риска дефолта не содержит финального решения. Backend валидирует версию и схему ответа, включая соответствие ID снимка, и отклоняет несовместимый ответ. Решение ссылается на конкретные результаты. Изменение данных после оценки требует нового запуска; прежний результат не перезаписывается.
- Переход статуса и запись `StatusEvent`/`AuditEvent` выполняются согласованно в транзакции. Оптимистическая блокировка защищает от двух одновременных решений. Окончательный исход доступен только уполномоченному сотруднику; основание обязательно, отклонение рекомендации фиксируется отдельно.
- Аудит содержит actor ID, роль, организацию/область, объект, действие, результат, время UTC, correlation ID, версию решения и основание. Изменение или удаление аудита через прикладной API запрещено. Доступ к журналу ограничен; экспорт/просмотр журнала тоже аудируется.

### Ошибки, отказоустойчивость и зависимости

- Для клиента ошибки имеют стабильный код и correlation ID без traceback, SQL, внутренних путей и сведений о чужом объекте. Для чужой заявки допустим единый ответ `404` без подтверждения её существования. Внутренний журнал содержит диагностический код без финансовых полей.
- Таймаут/недоступность мока, ошибка mock scoring или будущей ML-модели не превращаются в отрицательное кредитное решение. Попытка оценки сохраняется как ошибочная, ограниченно повторяется и выводится на ручной разбор; пользователь видит нейтральный статус обработки.
- Зависимости Python, npm и базовые Docker-образы фиксируются lock-файлами/версиями; доступные проверки выявляют известные уязвимости, лицензии и секреты. Обновления сопровождаются тестами контрактов и миграций. ML-участник версионирует модель и синтетические учебные данные; backend принимает только одобренную совместимую версию и не загружает произвольные сериализованные модели из пользовательского ввода. До приёмки модели используются только фиксированные тестовые сценарии mock scoring.
- Миграции выполняются контролируемо; резервное копирование и пробное восстановление БД нужны для любой долговременной демонстрационной среды. Healthcheck проверяет готовность приложения без раскрытия внутренних данных.

## Минимальный набор проверок перед демо

1. Прогнать матрицу доступа для обеих ролей, двух организаций и назначенного/неназначенного сотрудника по заявкам, истории, решениям и ленте.
2. Проверить запрещённые переходы, массовое присваивание, повторную подачу, конкурентные решения и корректность транзакционного аудита.
3. Проверить ошибочные и медленные ответы моков, падение скоринга, несовместимую схему/версию ответа, подмену ID снимка и восстановление обработки без ложного одобрения/отказа. Контрактные тесты должны проходить для mock и будущей модели.
4. Проверить отсутствие секретов и чувствительных полей в Git, образе, логах и ошибках; прогнать скан зависимостей и конфигурации контейнеров.
5. Восстановить чистую среду из Docker, миграций, seed и зафиксированных версий mock/правил; подтвердить одинаковый результат для одинакового снимка. После подключения ML-модели отдельно проверить её версию, валидационные материалы и воспроизводимость вызова.
