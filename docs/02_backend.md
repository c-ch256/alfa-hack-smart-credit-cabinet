  services/
    mocks.py         # ФНС/ЕГРЮЛ/ЕГРИП, БКИ — синтетика из JSON по ИНН
    checks.py        # DATA / FNS / BKI → check_results

Конвейер `process()` выполняется синхронно в запросе подачи (миллисекунды). В README опиши, что в промышленной версии он вынесется в воркер с очередью, а переходы останутся теми же.

## Бизнес-логика — требования
- **FSM**: таблица переходов `(from, to) → разрешённые роли` — единственный источник правды. Любая смена статуса идёт через `transition()`, который пишет `status_event`. Клиент может отозвать заявку из `manual_review` в `closed`; последующее решение сотрудника недопустимо. Недопустимый переход → HTTP 409.
- **Checking**: DATA (полнота по продукту), FNS, BKI → три записи `check_results` с `ok|warn|fail`, summary и payload. Стоп-фактор → `rejected`. Нехватка данных → `needs_info` с конкретным `info_request`.
- **Scoring**: сборка `ScoringRequest` из заявки, компании и моков → `scorer.score()` → запись `scores` (pd, risk_band, model_version, reasons, features).
- **Policy + оптимизатор**: строго правила 1–6 из п. 9. Кандидаты: сумма от запрошенной вниз шагом 10% до `min_amount`; сроки {запрошенный, +12, +24, … до `max_term`}; альтернативный продукт той же цели. Вызывать скорер на каждого кандидата (кэшировать одинаковые запросы). Возвращать `Decision{decision, rationale[], offer?}`, где rationale — человекочитаемые причины.
- **Offers**: при новом предложении старые `proposed` → `superseded`. Принять или отклонить можно только `proposed`.
- **Повторная проверка**: `additional-info` дополняет поля заявки и запускает `process()` заново; старые проверки и скоры остаются в истории.
- **Подписание и выдача (локальная имитация)**: `sign-demo/code` генерирует 6-значный код, хранит HMAC-хэш и срок жизни 5 минут, показывает код только внутри продукта без внешних SMS → `sign-demo` проверяет код за постоянное время → `accepted→signed_demo→disbursed_demo`. Формируется только демонстрационный договор и график из принятого предложения; реального подписания или перевода средств нет.
- **Recommendations**: детерминированные правила: `purpose_category` → семейство продуктов; проверка лимитов суммы и срока; предварительный расчёт платежа и DSCR по ставке группы B; ранжирование и причины («Подходит для покупки оборудования», «Срок до 84 мес. снизит платёж»); подсказка комфортной суммы.
- **Staff**: список и журнал всех фактически отправленных заявок без черновиков; карточка = анкета + компания + проверки + скор + предложения + история + DSCR по снимкам + решения с источником + внутренние заметки. Просмотр карточки и заметок аудируется. `POST /staff/loan-preview` оценивает условия конкретной заявки текущим Scorer без сохранения Score/Decision/Offer; результат предварительный. Решение `approve|counter|reject` с обязательным внутренним комментарием и повторной проверкой условий доступно только назначенному сотруднику из `manual_review`. `request-info` принимает список доступных клиенту полей и отдельный внутренний комментарий; публичный запрос формируется по шаблонам.
- STAFF-журнал показывает `status_at_event`, автора (`actor_user_id`, `actor_display_name`), компанию (`company_name`), ссылки на `decision_id`, `status_event_id`, `comment_id` и `offer_id`, а также исторические `offer_terms`. Комментарий решения берётся из сохранённого `Decision`, комментарий request-info — из `staff_comments`; публичная история их не содержит. Ошибки демо-подписания различают `INVALID_CODE` и `CODE_ATTEMPTS_EXCEEDED`.
- **Деньги** — int рубли; ставки — Decimal % годовых; время — UTC.

## Безопасность (обязательно)
- RBAC через зависимости `client_user` / `staff_user` на каждом защищённом бизнес-маршруте. Публичные `/health` и `/docs` локального FastAPI остаются доступными без токена; тест по OpenAPI проверяет 401 на защищённых маршрутах.
- Чужие клиенту заявки, компании, офферы → **404**. STAFF видит все отправленные заявки, но меняет только назначенную в `manual_review`. Клиент на `/staff/*` → 403.
- JWT HS256, TTL ≤ 8 ч, секрет из env (в `.env.example` — заглушка «change-me»). Пароли — bcrypt или pbkdf2 с солью.
- Rate limit на `/auth/login`: 5 попыток в минуту на логин+IP → 429 (in-memory допустимо, пометить «Допущение MVP»).
- Pydantic-валидация входа + бизнес-валидация лимитов продукта → 422 с понятным текстом на русском.
- `Idempotency-Key` на `POST /applications`; повторная подача → 409.
- Ответ клиенту не содержит pd, весов и сырого payload моков — отдельные DTO для клиента и сотрудника.
- Логи: метод, путь, статус, длительность, request_id; **без** персональных данных и токенов.
- `pip-audit` в CI или Makefile; контейнер от non-root; CORS только для origin фронта.

## Docker и окружение
- `docker-compose.yml` (ещё не создан): `db` (postgres:16-alpine, volume, healthcheck `pg_isready`), `api` (depends_on db healthy, внутренний healthcheck на `/health`), `web` (nginx: статика фронта + публичное проксирование `/api` → api). Текущие пути FastAPI `/health` и `/docs` не переименовываются; nginx позднее публикует их как `/api/health` и `/api/docs`, включая корректную загрузку OpenAPI через `root_path`/прокси.
- Старт `api`: `alembic upgrade head` → сиды, если БД пустая → uvicorn.
- Всё конфигурируется через env: `DATABASE_URL, JWT_SECRET, KEY_RATE, DEMO_PASSWORD, SCORER, MODEL_DIR, CORS_ORIGINS, LLM_BASE_URL, LLM_API_KEY, LLM_MODEL`.
- Ориентир по ресурсам: вся серверная часть ≤ 2 ГБ RAM в простое.
